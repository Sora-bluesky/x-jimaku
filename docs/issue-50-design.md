# Issue #50 設計: 文志向の節併合（翻訳単位の粒度を上げる）

Status: rev2（Sol Max 1 巡目の blocking 4 件を反映。再レビュー待ち）
Date: 2026-08-30
動機: 実地フィードバックが粒度に集中（「文単位で翻訳されるのでわかりにくい」/
「ケネディ・スペース／センター」分断 / 1 セッション 3 件の translate drop）。YouTube
パイプライン調査の結論「文完結の翻訳単位が最重要の持ち込める技法」と一致。#49 masking の
実装より先行する（2026-08-30 優先度昇格・Issue #50 コメントに記録）。

## 現状の事実（file:line）

1. 節分割は `MAX_CLAUSE_WORDS = 10`（`segmenter.ts:22`）で、句読点（. ? !）・カンマ・
   10 語超で切る（`findNextClauseBoundary` :1574 系）。**カンマや語数上限で文の途中でも
   切れる**のが粒度問題の根源。
2. 既存の短節持ち越し: `MIN_STANDALONE_CLAUSE_WORDS = 4`（:23）未満は `heldShortClause`
   （:240）に保持して次節へ前置。**4 語以上なら文の断片でもそのまま翻訳に流れる**。
3. 確定の時間上限は `AGREEMENT_TIMEOUT_MS = 6_000`（:26）。
4. 翻訳キューは `MAX_PENDING_TRANSLATIONS = 2`（translate.ts）で、溢れると最古を drop
   （実利用で 1 セッション 3 drop を観測）。

## 設計

### 方針: 「節」の確定はそのまま、**翻訳・表示への投入単位を文へ引き上げる**

LocalAgreement-2 による確定粒度（節）は変えない（確定安定性の資産）。確定済み節を
**文アセンブラ**（新設・segmenter 出力と翻訳投入の間）で束ね、次のいずれかで 1 翻訳単位
として放出する:

1. **文末**: 節末尾が sentence-final（`.` `?` `!`。略語ドットは #58 の単独大文字規則を
   再利用して除外）に達した
2. **語数上限**: 束の合計が **20 語**に達した（≥ MAX_CLAUSE_WORDS×2。翻訳プロンプトと
   cue 分割（≤28 units×n）が処理できる範囲）
3. **時間上限**: 束の**最初の確定節がアセンブラに入ってから放出まで**を 4 秒で打ち切る。
   この 4 秒はアセンブラ滞留のみの上限（表示までの総遅延は認識・翻訳・表示待ちが別途
   加算され、動画停止中の表示待ちは無期限になり得る。総遅延の上限は主張しない）。
   タイマーは放出・破棄・destroy の全経路で必ず取り消す。
4. **フラッシュ**: EOS・stop-flush・無音確定（既存の flush 経路）では即時放出

- 放出単位が従来の「節」より長くなるため、**翻訳 1 回あたりの内容が文になる**（誤義・
  文脈切れの改善が期待される副次効果。#49 の前提も良くなる）。
- 表示側は現行のまま（cue 分割 `splitCueText` が 28 units 超を分割するので、長い文単位でも
  表示契約は壊れない。表示スタイルの追記型バッファは別 Issue）。
- 翻訳 drop への効果: 投入レートが下がる（節数 → 文数）ため `MAX_PENDING_TRANSLATIONS=2`
  の溢れ頻度が構造的に減る。キュー深さは触らない（1 レバー 1 計測）。
- 実装位置: `offscreen/index.ts` の `onLine` に文アセンブラを挟む。**「segmenter 内部
  不変」は撤回**（レビュー 1 巡目）: `onLine` だけでは stop-flush / EOS / 無音確定を
  識別できないため、segmenter に**最小の flush 通知**（`onFlushCompleted(reason)` 型の
  コールバック・flush 済み経路の末尾で発火）を追加する。明示停止の順序は
  「`segmenter.stop()` → 末尾節 `onLine` → flush 通知 → アセンブラ放出 →
  stop-flush enqueue → drain」に固定し、v0.4.5 の drain が期待する「stop 時に最終節が
  キューへ入っている」状態を保つ。interim（非 final）行は素通し。
- **束の ID は最後の確定節の ID**（先頭 ID だと後続 interim を確定時に消せず残表示になる。
  連番の欠落は許容）。列挙済みの消費者（翻訳キュー・background の ID 別 Map・字幕再送・
  options の ID 別要素・overlay の保留/重複排除/順序判定/cue ID・bench 収集）は
  「最後の ID」で整合する。

### 決定表（放出条件の網羅）

| 入力 | 動作 |
|---|---|
| final 節・文末で終わる | 束に加えて即放出 |
| final 節・文中 | 束に追加。語数 ≥20 なら放出、そうでなければ 4 秒タイマー設定（未設定時のみ） |
| interim 行 | 素通し（束に触れない） |
| EOS / stop-flush / 無音 flush | 束を即放出（空なら何もしない） |
| 新キャプチャ開始・destroy | 束を破棄しタイマー取消（requestId 不一致の残骸を作らない） |
| タイマー発火 | その時点の束を放出 |
| SW 再起動・grace 再接続・タブ切替 | **束を保持**（終了条件ではない。復旧後に続きを束ねる） |

## 受け入れ

1. 単体テスト: 放出条件 6 行の全ピン（文末即時・20 語上限・4 秒タイマー・flush・破棄・
   interim 素通し）。略語ドット（U.S.）で放出しないこと。
2. live2 tts2 after: 誤訳が改訂 ref before（5）から悪化しないこと（judge のみ。
   平均語数は live2 では測れない。表示分割後の日本語しか採れないため）。
3. **放出単位の実証は CfT bench**: 認識ログの EN 節（= 放出単位）から**放出あたり
   平均語数の before/after** を機械算出する（上昇が期待値）。cue latency の主張はしない
   （現行結果に指標が無い）。
3b. tts after（live2）: 誤訳 before(10)+2 以内・**translate drop 警告 0 件**（95 秒採取中）。

4. 実機: sora 体感確認（「文単位でわかりにくい」の再評価。数値ゲートではなく所感の記録）。
5. CfT WER: tts/base ×2 帯内（clauses 数の減少も記録。cue latency は現行結果に指標が
   無いため主張しない）。
6. Grok 敵対レビュー → CI → Codex Bot。
