## 背景 — 3 エラーは 1 本の因果鎖（分析の結論）

SW port 切断 → content 側が全面テアダウン（overlay 破棄・translator リセット・辞書クリア・
tap 停止）→ 再接続で新 tap が採番 0 から送信 → offscreen の expectedPcmSequence は据え置き →
「PCM sequence gap」警告。**切断〜再接続の間の音声は tap 破棄により実際に失われている**
（Sol レビューで確定 — 採番リセットは「実害ゼロ」ではない）。キュー溢れだけが独立事象で、
真因は split/merge の構造的非対称性 + バースト吸収不足（翻訳レイテンシではない）。

## 2-A 最後の未処理エラーの観測（「死因」ではない — best-effort の記録）

- **background**: 先頭で `self.addEventListener("error" / "unhandledrejection")` を登録し、
  `chrome.storage.session` に「最後の未処理エラー」（at・context・message・stack 先頭 500 字）を
  書く。**best-effort**（SW 終了イベントではないため取り漏らしはあり得る — 名称・文言に
  その含意を残す）。起動時 hydrate で前回レコードがあれば固有文言で 1 回だけ console.warn し消費
- **offscreen**: chrome.storage 不可（chrome.runtime のみ・公式 doc 確認済み）。global handler は
  既存 port で `OFF_DIAGNOSTIC {kind:"unhandled-error", ...}` を background へ送り、background が
  同じ storage.session 面に永続化。port 不在時は 1 件だけメモリに保持し再接続時に送る
- **ハードクラッシュは自己申告不能**: background の既存 offscreen 切断オブザーバ
  （inspectUnexpectedOffscreenDisconnect 周辺）に「offscreen disappeared without a recorded
  error」の推定消失レコードを追加（固有文言）
- メッセージ型は shared/messages.ts に追加（isMessage バリデーション込み）

受け入れ: dev ビルドで人工 rejection を background / offscreen 各 1 回発火 → 次回起動 warn で
記録が読めること（作動の確認）。

## 2-B キュー溢れ修正 — 明示の遅延予算付きペーシング

現状の欠陥（overlay.ts:897-913, 1096-1106, 1147-1181）:
1. splitCueText の分割兄弟は結合すると常に 28 units 超 → マージ必ず失敗
2. acceleratedUntilDrained が drop と同一呼び出しで立つ → 加速が効く前に落ちる
3. 深さ 2（+active 1）はバーストを吸収できない

**凍結するポリシー（Sol blocking 2 への回答）**:
- **表示待ちの排出所要時間予算 = 6.0s**。キューは「今のペーシングで全部掃けるまでの推定時間」が
  予算内に収まる深さまで保持し、超える分は最古から drop する。drop は例外でなく**意図した
  上限挙動**として `cueDrops` カウンタ + レート制限付き warn で記録する
- 実装形: `MAX_WAITING_CUES = 6`
- **ペーシングの優先規則（一意・再レビューで凍結）**: `acceleratedUntilDrained` が立っている間は
  **全深度で CUE_ACCELERATED_DISPLAY_MS = 1.0s に固定**し、キューが空になるまで維持（既存
  フラグの意味論そのまま）。よって深さ 6 の排出所要 = 6 × 1.0s = **予算 6.0s が厳密に成立**。
  動的減衰式は採用しない（1.0s は floor でなく加速中の固定値）。非加速時は従来どおり 1500ms
- **予測的加速**: `waitingCues.length >= 2` で acceleratedUntilDrained を立てる（溢れる前）。
  バーストは 1 enqueue ループ内で同期 push されるため加速はループ中の排出には効かない —
  効かせる相手はループ後の表示ペーシングであり、それで足りる（drop 判定は深さ 6 が受け持つ）
- 閾値横断時に `rescheduleCueAdvance()` を必ず呼ぶ（加速が現在表示中の cue にも効くように）
- **最悪遅延の明示**: 好意的 6-cue バーストでも末尾 cue はセグメント末から ~6s・セグメント開始
  から最大 ~14s 遅れる。これは 8s セグメント上限という上流の性質による下限であり、本設計の
  守備範囲は「予算 6s を超える保持をしない」こと。より根本の遅延削減（split-on-display・
  セグメント短縮）は v0.4.3 以降
- 棄却済み: 表示時間の一律短縮（可読性破壊）/ split-on-display（波及大・別段）

受け入れ（テスト）: **「表示直後の active 1 + 待ち 6」から空になるまでの経過時間 ≤ 6.0s
（+ active 残余 ≤ 1.5s）を fake timer で assert**（保持数でなく排出時間を縛る）。
**連続バースト**（6 cue × 2 連続）で「予算内保持 + 超過分の意図的 drop + カウンタ計上」を
テーブル駆動で検証。実機: 早口動画 run で cueDrops before/after 比較。
pause 中の到着・加速中 seek・fade 中の新着の 3 レースは既存フリーズ機構と干渉しないことを
単体テストで縛る（Sol 指摘 5 の列挙）。

## 2-C PCM sequence の弁別（誤報の解像度を上げる — info 化はしない）

- offscreen 検知器を分岐（どちらも warn のまま・文言を固有化）:
  - `received < expected`: 「pcm sequence restarted after recovery; audio during the
    disconnect was not captured」— 採番リセット = 復旧イベント。**切断中の音声は実際に
    失われているため warn を維持**（info 化は v0.4.3 の非破壊テアダウンで連続性が保証されて
    から再判断）
  - `received > expected`: 「lost N pcm chunks in transit」を差分 N 付きで warn
  - 追従（expected = received + 1）は維持
- **relay 無音 drop の可視化（分類 + 集約）**:
  - 対象: background relayContentPcm の 3 経路（captureState 不一致 / offscreenPort null /
    postMessage 例外）+ content 側送信失敗（port null / postMessage 例外・index.ts:1825 相当）+
    offscreen の decode 拒否
  - **正常系は数えない**: 停止処理中（captureState が stopping/idle へ遷移した後）の stale PCM
    は意図された破棄なので除外
  - per-reason の**メモリ内カウンタ**に集約し、レート制限付きで 1 行のサマリ warn
    （例: 「pcm relay drops since capture start: {reason: count}」）。**per-chunk のログ・
    storage 書込みは禁止**。キャプチャ停止時に非ゼロならサマリを 1 回出す
- 採番の単調化（epoch 付与）と無音パディングは入れない（v0.4.3 後の実測で判断）

受け入れ: ベンチ回帰なし。実機で復旧イベント時に新文言 warn が出ること（弁別の作動確認）。
