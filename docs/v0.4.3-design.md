## 切断の 2 シナリオ（現状の要点）

- **A: SW 死 → 再起動**: content 即全面テアダウン（content/index.ts:660-714）。新 SW は
  hydrate で recoveryPending を立て（background/index.ts:670-673）、
  reconcileRecoveredCapture が同一 requestId の CS_START_TAP を再送（:1899-1994）
- **B: SW 生存下の content port 断**: background が即 requestCaptureStop
  （:1077-1112）。**recoveryPending は立たず、port 再登録トリガー（:1165）も
  reconcile も動かない**（Sol blocking 1）— B には現状、再開遷移が存在しない

好条件（確定済み）: offscreen document は SW 死を生存し認識状態を保持 / overlay は
chrome API 非依存 / tap の sanity check・overlay タイマーは port 非依存 / 故意の port
差し替えは expectedContentDisconnectPorts で既に保護（:995 — 新猶予より前に判定を維持）。

## 状態機械（Sol blocking 2 への回答 — タイマーは「エピソード」に束ねる）

**猶予エピソード** = `{requestId, tabId(bg側のみ), portGeneration, deadlineAt(絶対時刻)}`。
portGeneration は background が content port 登録ごとに tab 単位でインクリメントする世代番号。

- 切断検知でエピソードを開始し `deadlineAt = now + GRACE_PERIOD_MS(3_000)`
- **再切断はエピソードを延長しない**: 既存エピソードが生きていれば deadlineAt を据え置く。
  **エピソードの終端は「resume ACK の受領」または「満了処理の完了」のみ**（最終巡指摘:
  CS_START_TAP 送信では閉じない — 送信後・受領前の再切断が新期限を得る穴を塞ぐ）
- **resume ACK** = 新世代 port から届く同一 requestId の `CS_TAP_STATE {state:"tapping"}`。
  background はこれを受けて初めてエピソードを閉じる（content の tap 生存 resume 分岐は
  従来どおり tapping を必ず返す — これが ACK を兼ねる。ended-awaiting-resume の場合は
  tap を作らないため `CS_TAP_STATE {state:"stopped", detail:"ended-awaiting-resume"}` を
  ACK として返し、background はセッションを EOS 済みとして扱う）
- タイマー発火時は**エピソード同一性の全量比較**（requestId + tabId + portGeneration +
  deadlineAt）で再検証し、一致時のみ満了処理（stale timer が後続エピソード・新セッションを
  殺さない）
- content 側は setTimeout に加えて**次回イベント時に deadlineAt を突き合わせる**
  （hidden タブでタイマーが遅延しても、満了後に届いたメッセージ処理側が期限超過を検出して
  満了処理へ落とす）
- SW 側タイマーは SW 死で消えるが、その場合はシナリオ A の hydrate/recoveryPending 経路が
  受け持つ（persist は不要 — 満了処理は「停止」でありデフォルト挙動と同じ側に倒れる）

## 変更

### C1. content: 切断時テアダウンを猶予エピソードに変える

- 対象: content/index.ts:660-714 の通常切断分岐。**拡張 context 死の分岐（:646-657）は
  現状維持し、バッファ等の猶予状態もそこで必ず破棄**（拡張更新の挙動不変 — Sol 指摘）
- 猶予中はセッション状態（session/requestId・path・hint・辞書・translator・overlay・tap）を
  保持。再接続ループは従来どおり
- **resume（成功遷移）**: 再接続後に同一 requestId の CS_START_TAP を受信（既存 tap 生存分岐
  :761-787 を拡張）→ エピソード終了・バッファ flush・全状態継続
- **満了 / 明示 CS_STOP_TAP**: 現行の全面テアダウン。満了後に同一 requestId の
  CS_START_TAP が来た場合は**今日と同じ fresh start**（自動復帰は現行 reconcile の既存挙動で
  あり、再トグル要求はしない — 意味論を明文化）
- **別 requestId の CS_START_TAP**: 猶予を即終了し、**直列化**: 旧 tap の stop 完了を待って
  から新 start（現状 :789/:1221 の another-tap-is-active 衝突を避ける。既存の
  enqueueTapOperation の直列キューに乗せる）
- **EOS 中の切断（Sol blocking 3）**: track-end で activeTap は null だが session は保持される
  状態を `ended-awaiting-resume` として明示的に扱う: lastEosRequestId / endedAudioTapTarget を
  猶予中も保持し、resume の CS_START_TAP では **tap を再作成しない**（動画は終わっている）
  — presentation を破壊せず、既存の「同一 requestId + tap なし」= preservePresentation 経路を
  「translator リセット・overlay 破棄をしない」形に修正する

### C2. content: 猶予中の送信バッファ（CS_PCM + CS_EOS）

- 容量 **16 chunk 相当**（3s = 12 + 位相/ジッタ/端数 PCM/EOS の余裕 4 — Sol 指摘の
  boundary+final partial+EOS を吸収）。超過は最古 drop し recordPcmSendDrop("buffer-overflow")
- **flush の再入制御**: flush は同期の非再入ドレイン。flush 中に生成された新 chunk は
  flush キューの後ろに並ぶ（送信順 = seq 順を保証）。送信失敗（flush 中の再切断）は未送分を
  suffix ごと保持したままエピソード継続（同一エピソード内なので期限は据え置き）。
  再 flush 時の重複送信はしない（バッファから取り除くのは post 成功後）
- 拡張 context 死・満了・別 requestId で破棄

### C3. background: 切断即停止を猶予 + 明示 resume に変える（シナリオ B）

- port onDisconnect（expectedContentDisconnectPorts 外・capture active）で即
  requestCaptureStop せず、猶予エピソード `{requestId, tabId, deadlineAt}` を開始
  （captureState は running のまま）
- **resume 遷移を新設（Sol blocking 1）**: registerContentPort で同一 tab の port が再登録
  されたら、エピソードが生きていて requestId が現 captureState と一致する場合に限り、
  **CS_START_TAP {requestId, settings: 凍結済み session.settings} を直接送る**
  （reconcile は経由しない — recoveryPending は A 専用のまま触らない）。settings は切断時点の
  凍結値（猶予中の設定変更は次セッションから — 明文化・テスト対象）。
  **エピソードはここでは閉じない**: 新世代 port からの ACK（CS_TAP_STATE tapping /
  ended-awaiting-resume）受領で閉じる。ACK が deadlineAt までに来なければ満了処理
  （requestCaptureStop）— 期限は据え置きのまま
- 満了で requestCaptureStop("content-port-disconnected")（従来文言）
- **tabs.onRemoved はエピソードを明示キャンセル**してから既存の停止処理（順序保証に依存しない）
- 発火時再検証: captureState.requestId がエピソードと一致しない（別セッションが始まった/
  正常 stop 済み）なら何もしない

### C4. 再開時の background→content メッセージ整合（1 巡目の記述を修正）

- postCaptionClear は stopping/idle/**error** で、postStopToContent は stopping のみで発火する
  （:1146）。C3 により「切断だけ」では stopping に倒れなくなるため、猶予内 resume では
  どちらも送られない。stop クリック・満了・タブ閉鎖・offscreen 不整合による発火は**正当**で
  現行どおり（これらは実際に停止すべき事象）

### C5. 認識結果のエンドツーエンド配達保証（最終巡指摘で全面組み替え）

区間が 2 つある: offscreen→background（A でのみ切れる）と background→content（A・B 両方で
切れ得る。現状 OFF_RECOG は hydration を待たず、content port 不在なら転送先なしで消える —
background/index.ts:1485, :2564。B では offscreen port が切れないため offscreen 側バッファ
だけでは 1 行も守れない）。

- **offscreen 側**: final の OFF_RECOG をリングバッファ（32 行上限）に保持。保持条件は
  「port null」に加え **postMessage 例外時も**（offscreen/index.ts:1419 の例外経路）。
  interim はバッファしない（一過性）。**自発 flush はしない** — background から
  `OFF_FLUSH_RECOG {requestId}` 要求を受けたときだけ、requestId 一致分を順序どおり送る。
  キャプチャ停止・新 requestId で破棄
- **background 側**: resume ACK 受領（= content port 生存・状態 active が確定した時点）で
  `OFF_FLUSH_RECOG {requestId}` を offscreen に送る。以降の OFF_RECOG は通常経路で
  content へ流れる（状態は active なので :1485 の破棄条件に当たらない）。
  シナリオ A では hydration 完了 + reconcile の CS_START_TAP + ACK の後に送られるため
  「hydration 前に flush が届いて捨てられる」レースが構造的に消える
- **順序整合（レビュー確認済みの前提）**: overlay は raw final を保持し同一 ID の ja 付き
  final（または path none）で解決する（overlay.ts:826 の pendingFinals）。flush は
  raw→ja / raw→none の両順序をテストで縛る
- メッセージ追加: OFF_FLUSH_RECOG（messages.ts に型 + validator）
