## 1-1 無音ヒントの原因別案内（誤処方箋の修正）

### 現状（code-reader 採取・file:line 裏取り済み）

- 発火条件: background が RMS < 0.001（SILENT_INPUT_RMS_THRESHOLD, background/index.ts:71）を
  10 秒（SILENT_INPUT_HINT_DELAY_MS, :72）観測 → SW_SILENT_INPUT{requestId, showHint} を
  content へ（:1405-1499, :1532-1553）
- 表示: overlay.ts:1808-1816 で文言固定「▶ 音声がありません — 動画を再生してください」
- content は AudioContext の suspended を知っている: audio-tap.ts:267-295 resumeOrDefer /
  :297-314 installResumeListeners。遅延 resume 成功のコールバックは audio-tap.ts:347-356

### 実測された誤案内（2026-08-28 実機）

復元タブで AudioContext が suspended のまま → ヒントは「動画を再生してください」だが、
動画は再生中で、正しい処方箋は「ページをクリック」（それでも直らない場合「タブを開き直す」）。
UX 文脈: x.com はスクロールでオートプレイが普通 = クリックは通常動線にない操作なので、
案内しない限りユーザーは辿り着けない。

### 変更（Sol Max レビューの決定表・seam 指示を採用）

- メッセージプロトコルは変更しない（SW_SILENT_INPUT {requestId, showHint} のまま。
  content/index.ts:538-559 の既存ガードも維持）
- content 側に **純関数 resolver** を新設し、variant を導出する。**showHint（background 由来）を
  真実の源として保持**し、variant は overlay 更新の直前に毎回導出する（遅延 tap イベントが
  showHint:false 後にヒントを復活させる事故を防ぐ）
- overlay の seam は setSilentInputHint(variant | null)（null = 非表示）。boolean 経路は残さず
  呼び出し側を全部更新する

決定表（優先順位順・全入力クラス網羅。tap ∈ {missing/starting, suspended, running,
stopping/closed} × video ∈ {missing/replaced, playing, paused, ended} × visibility ×
hint ∈ {off, on}）:

| 優先 | 条件 | 結果 |
|---|---|---|
| 1 | hint off | 非表示 |
| 2 | hint on・タブ hidden | 保留（hint 保持・visibility 復帰時に再評価） |
| 3 | 対象 video（connected）が paused か ended | paused 案内（現行文言維持: 「▶ 音声がありません — 動画を再生してください」） |
| 4 | 対象 video 再生中かつ現行 tap が suspended | gesture 案内: 「▶ 音声を取得できません — ページ内を一度クリックしてください」 |
| 5 | 残り全部 | unknown 案内: 「▶ 音声がありません — タブを開き直すと直ることがあります」 |

**paused が gesture に勝つ**理由: 再生ボタン押下は resume ジェスチャ（audio-tap の
play capture リスナー）も兼ねるため、「再生してください」で両方直る。

resolver の再評価トリガー（1 箇所の関数を全部から呼ぶ）:
SW_SILENT_INPUT 受信 / tap.start() 完了（初期 suspended は start() の戻り値であり
onDetail を通らない点に注意）/ AudioContext statechange（**新規に購読** — 後発 suspension
の検知に必要）/ tap の set・clear / target video の set・clear / video の
play・playing・pause・**ended**（ended は現行リスナーに無いので追加）/ visibilitychange。

### 併せて 1 件（同じ機構の別の欠陥を 1 つ探す規律による）

audio-tap.ts:274-278 の「immediate AudioContext resume was rejected」console.warn は、
オートプレイ世界では想定内（deferred resume リスナーが後続で回収する設計）なので
console.info へ格下げ。Chromium 自身が出す「The AudioContext was not allowed to start」は
ページ gesture なしで resume を試みる限り Chrome 側が出すため抑止不能だが、正常動線では
suspended にならないことを実測済み（2026-08-28 の成功 run ではエラー一覧に出ていない）。
復元タブ等の異常系でのみ出るのは「ユーザーが対処すべき実失敗」の記録として許容。

## 1-2 powerPreference 警告の発生源断ち（Sol Max の node_modules 実査で確定）

### 事実（Sol Max 実査）

- 自コードの requestAdapter() は 4 箇所とも引数なし。`powerPreference` は src/ にゼロ件
- 発生源: **Transformers 4.2.0 が `ONNX_ENV.webgpu.powerPreference = "high-performance"` を設定**
  （node_modules/@huggingface/transformers/dist/transformers.web.js:7800）し、
  ORT 1.26.0-dev が requestAdapter へ転送（onnxruntime-web dist/ort.webgpu.mjs:3237-3251）。
  native EP 側にももう 1 つの adapter 要求（dist/ort-wasm-simd-threaded.asyncify.mjs:79）が
  あり、警告 ×2 と符合
- 設定は worker ローカル（whisper.worker は offscreen/index.ts:1071-1078 が作る module worker
  内で動く）。公開されている注入点: `env.backends.onnx.webgpu.{powerPreference,adapter,device}`

### 変更

**whisper.worker 内・Windows のときだけ**、Transformers 読み込み後に
`env.backends.onnx.webgpu.powerPreference` を **undefined に戻す**。

- Windows では powerPreference は Chromium が無視する（警告文そのものが根拠）ので、
  GPU 選択の実挙動は不変。警告だけが消える
- 他プラットフォームは触らない（high-performance が実際に効く環境の GPU 選択を壊さない —
  Sol blocking 2 の後段の指摘）
- adapter/device 注入方式（env.webgpu.adapter / EP device hook）は採らない: JS 側 1 要求しか
  回避できず（native EP の要求が残る）、選択性の変更リスクもあるため
- 実装時の検証: worker 内で requestAdapter の引数を一時観測し、Windows で
  powerPreference が渡らなくなったこと・警告が出ないことをベンチ（--trace）で確認。
  もし native EP 経路が env を読まず警告が残る場合は fail loud で報告し、README 記載
  （上流由来・実害なし）へフォールバック
